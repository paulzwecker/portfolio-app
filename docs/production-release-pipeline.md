# Coordinated Production Release Pipeline

**Status:** Implemented in the M1 feature branch; not activated or live-tested. The workflow is manual and must be configured and reviewed before use. No production migration, deployment or database change was performed while preparing this document.

## Release contract

`.github/workflows/production-release.yml` is the only proposed production release path. It is manually dispatched from `main`, requires the exact current main SHA and green CI for that SHA, serializes releases, and deploys API and web artifacts from that same checkout. Before creating a deployment, it checks provider deployment history for the exact release SHA. A verified existing live/ready deployment is reused; an in-progress deployment is followed; failed, terminal, ambiguous or incompletely scanned history stops the release instead of creating a second deployment. The workflow does not import workbook data, run provider ingestion, accept financial-model or research proposals, recompute investment decisions, or activate recurring jobs.

The release sequence is:

1. Validate the selected SHA, current `main` tip, CI checks, one-owner approval policy and main-only secret scopes.
2. Run the read-only Neon/Render/Vercel preflight. Verify target identity, schema head, complete table counts, current recovery requirement, provider readiness and disabled background-operation flags. No production write credentials are available in this stage.
3. Validate the migration checkbox and typed confirmations against the read-only results. Then pause once at the credential-free `production-release-approval` environment. The repository owner manually approves the exact SHA and requested scope. A schema mismatch or missing confirmation stops before the approval pause.
4. If and only if the database is exactly at reviewed base `6c2eaf0b8147` and the release repository head is `9f2a6d4c81b7`, apply only `npm run db:migrate` with the guarded production writer URL and authorization enabled. If the initial database contains only the four allowed baseline reference tables, require the exact empty-baseline acknowledgement instead of a recovery branch; if any other table has rows, verify a fresh recovery branch. If the database is already at `9f2a6d4c81b7`, skip migrations. Any other head stops the release for review.
5. Reverify the migration target, base head, applicable recovery protection and exact confirmation with the read-only URL and write authorization disabled. After migration, run `production_release schema-check` through the separate read-only URL and read-only PostgreSQL session; it does not reuse the migration engine or writer credentials. Finally, recheck the exact head.
6. Deploy the exact SHA to Render, require its deploy record to report that commit as live, and wait for `/health/ready` to return `database=connected` and `schema=current`.
7. Install the pinned Vercel CLI before exposing credentials, link the project and pull production build settings in a step-scoped token operation, remove the pulled `.vercel/.env.production.local` cache, and build the checked-out SHA with an allowlisted environment that excludes deployment/GitHub tokens. Then deploy the prebuilt artifact tagged with the release SHA and verify its project, status, commit metadata and production alias. Runtime environment values remain configured on the Vercel project; they are not copied into the local build process or artifact by this workflow.
8. Run direct API and authenticated web-to-API read-only smoke checks.
9. Publish a sanitized workflow summary and a 90-day release evidence artifact. These records are useful audit evidence, not tamper-proof storage; repository administrators can delete workflow records and artifacts.

`cancel-in-progress: false` prevents a second production workflow from interrupting an active release. The workflow rechecks that the approved SHA remains the `main` tip before migration and deployment; a newer main commit stops the old release. Render history is scanned in bounded 100-deploy cursor pages; Vercel history is scanned in bounded 100-deployment production pages scoped to the exact project/team. If the five-page limit is reached before the provider reports the end of history, the release fails closed. GitHub concurrency and provider history checks prevent duplicate releases through this workflow and make retries idempotent when the provider recorded the prior request. They cannot serialize an independently initiated provider-dashboard/API deployment that races with the final check; keep provider deploy credentials restricted and use the coordinated workflow as the sole production path.

### Repository and plan capability check

Read-only GitHub API inspection on 2026-11-04 confirmed `paulzwecker/portfolio-app` is a public repository owned by `paulzwecker` (repository owner account ID `149177174`). The environment endpoint currently lists only `main - portfolio-api`, with no protection rules. None of the six release environments or their branch policies are configured yet. The GitHub connector does not expose the owner's billing-plan tier. This does not block the required reviewer feature on the present public repository: GitHub documents environment required reviewers for public repositories on all current plans; legacy per-repository plans are excluded. If the repository becomes private, the account needs a plan that supports environment protection rules.

GitHub required reviewers support one-or-more reviewers, and self-review blocking is an optional environment setting. A single developer cannot approve a workflow they started when **Prevent self-review** is enabled. The single-owner setup below requires that option to be off on one credential-free approval environment. The trusted validator also requires the repository owner to initiate the workflow; the owner then manually approves the exact release after the read-only cloud preflight succeeds. This is one approval for the whole release, including a migration when requested. The separate migration checkbox, exact target-bound confirmation and empty-baseline acknowledgement remain mandatory where applicable.

The workflow retains five distinct credential environments and adds one credential-free approval environment:

| Environment                   | Reviewer rule                                                                             | Branch rule | Contents                                               |
| ----------------------------- | ----------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------ |
| `production-release-approval` | Exactly the repository owner (`paulzwecker`, ID `149177174`); `prevent_self_review=false` | `main` only | No secrets or variables                                |
| `production-readonly`         | None                                                                                      | `main` only | Read-only database and provider inspection credentials |
| `production-migration`        | None                                                                                      | `main` only | Migration role and read-only verification credentials  |

| `production-web`              | None                                                                                      | `main` only | Vercel deploy token                                    |
| `production-smoke`            | None                                                                                      | `main` only | Web smoke-test login                                   |

The trusted validator reads the repository owner ID through the GitHub API and requires that exact owner both as the workflow initiator and sole user reviewer. It verifies the approval environment has `prevent_self_review=false`, exactly one reviewer rule and only a `main` branch policy. It verifies the five credential environments are `main` only and contain no reviewer, wait-timer or other protection rules that would add extra approval pauses. The workflow fails closed when any environment or branch policy is missing or differs. GitHub's environment read API does not expose the administrator-bypass toggle, so verify **Allow administrators to bypass configured protection rules** is unchecked in repository settings. GitHub documents required reviewers for public repositories on current plans (except legacy plans); the repo's public visibility was verified, but the exact account billing tier is not exposed by the connected API. See [GitHub environment capabilities](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments), [environment protection rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), and the [REST environment response](https://docs.github.com/en/rest/deployments/environments).

The release workflow grants its `GITHUB_TOKEN` only contents, checks, Actions and deployment-record access needed by the selected jobs. It does not need a personal access token. The selected SHA must have successful CI check runs named `Quality, contracts and build`, `PostgreSQL integration tests`, and `Windows migration command compatibility`.

Use distinct read and deploy credentials. The migration environment needs its own copy of `PRODUCTION_READONLY_DATABASE_URL` because GitHub environment secrets are scoped to one environment. The workflow places read-only database URLs, Neon keys and recovery URLs on only the specific preflight or verification step that needs them; checkout, dependency installation, and GitHub API checks do not receive database credentials. The pre-migration check verifies the exact target, reviewed head, recovery point and confirmation through the read-only guard. Only the `npm run db:migrate` step receives the production writer URL and `DATABASE_PRODUCTION_WRITES_AUTHORIZED=true`; the migration command itself revalidates its target with the existing write guard. Post-migration schema-drift and head checks use the read-only URL with authorization false. Secret-bearing Python commands set `UV_NO_SYNC=1`; locked dependencies are installed in the earlier credential-free setup step so `uv run` cannot synchronize packages while production credentials are present. The pinned Vercel CLI is installed before its token is introduced. The web build runs separately with a narrow environment allowlist and no Vercel/GitHub deployment tokens. The production env cache written by `vercel pull` is deleted and verified absent before the build, while runtime values remain managed in Vercel project settings. Only project link/pull and the final prebuilt deployment steps receive the Vercel token. Do not copy the web/API runtime token into the workflow unless a future, documented smoke endpoint requires it. Never print provider responses containing env values or post credentials in CLI arguments in local terminals.

Only `production-release-approval` is a manual reviewer gate. It runs after exact-SHA/CI verification, read-only cloud preflight and a no-secret input-plan check. The approval environment contains no credentials. All later production jobs depend on this approval and keep the existing per-purpose secret scopes. The migration job sets `DATABASE_PRODUCTION_WRITES_AUTHORIZED=true` only inside the guarded `npm run db:migrate` step, after exact target verification, current base/recovery checks and typed confirmations. It uses the existing database write guard, not offline SQL or a raw driver. All data/provider operations remain disabled.

## Initial release migration review

The live production branch was last independently verified on 2026-11-03 at PostgreSQL 18.6, database `neondb`, Alembic `6c2eaf0b8147`. It had 89 public tables and 20 rows total in four populated tables: one Alembic version row, 11 ranking definition rows, four return methodology definitions and four score definitions. No canonical company, holding, target or accepted-model rows were present. Rerun preflight before any release; these are dated observations, not current guarantees.

The single local Alembic head is `9f2a6d4c81b7`, with this linear upgrade:

```text
6c2eaf0b8147
  -> b16d4f8a2c91  workbook sync artifacts, schema approvals, runs/previews; job-name check extension
  -> c17a0b9d4e62  permit production in two bootstrap-run target checks
  -> 3e5c8a1d7b42  model-only identity bootstrap receipt table
  -> 9f2a6d4c81b7  agent model revision proposal table and indexes
```

Review of the checked-in migration files found no data backfill. The first, third and fourth revisions add tables/indexes. `c17a0b9d4e62` replaces two check constraints to include `production`. Downgrades drop newly created tables and their stored state; the constraint downgrade narrows allowed values and could fail if production-target rows exist. **Do not automate Alembic downgrade as rollback.** If a migration fails or a later deploy fails, stop the release, preserve the new schema, keep the existing API running where compatible, verify exact state read-only, and obtain an owner decision for a forward fix or a separately rehearsed Neon restore. A Neon child branch is a restore point, not an automatic rollback of the primary.

The initial migration may proceed without a long-lived Neon recovery branch only when the fresh read-only inventory contains rows solely in the reviewed nonessential baseline tables `alembic_version`, `ranking_definitions`, `return_methodology_definitions` and `score_definitions`. Any row in any other table, including an unknown future table, requires a fresh recovery branch. The migration job rechecks the full table inventory immediately before applying. When no branch is required, the operator must enter `ACCEPT INITIAL EMPTY BASELINE WITHOUT RECOVERY`; if any other table has rows, that acknowledgement is rejected and recovery verification is mandatory.

When recovery is required, the branch must be a direct child of the verified primary, ready, same database/PostgreSQL version/current schema and table-count inventory, created in the last four hours, and not expiring within the next day. The workflow never creates, deletes, promotes or extends a Neon branch. A currently known recovery child at Alembic `12a6f0d9c3e1` is stale and must not be reused. After accepted financial, portfolio or other application data is present, all migrations require a verified recovery point under this policy.

The PostgreSQL migration rehearsal remains a required CI check and local integration suite. If an initial migration fails without a recovery point, stop the release before API/web deployment, preserve the resulting database state, check the Alembic head and schema read-only, and obtain an owner decision. Do not run an automatic downgrade or reset. Because the operator accepts loss of the nonessential initial baseline, a separately reviewed re-provisioning plan may be considered only after confirming there is still no accepted application data. Once accepted data exists, recovery or a rehearsed forward repair is required; the workflow never performs restore operations.
